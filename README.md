# Pico Timing Box

This is the repository for (almost) all things related to the Raspberry Pi Pico powered timing boxes that are used by the [SPIM and spimGUI](https://github.com/jmtayloruk/spim-interface.git) to schedule the triggering of cameras and lasers etc for prospective optical gating. These pico based timing boxes implement a subset of the existing xmos-xs1 timing box protocol, with 4 BNC outputs and the onboard LED. The current host software also has a dedicated Pico timing-box type. Two of the outputs are permanently wired to a $10k\Omega$ impedance, and two are switchable between the high impedance ($10k\Omega$) mode and a low impedance mode ($50\Omega$) via a pair of switches in side the timing box. We originally had 10 units produced by European circuits however due to some mis-communications they need to be modified to be full operational (see the [hardware modification notes](timingBoxModicationInstructions.md))

## The Pianola Concept

To synchronise the triggering of different cameras, lasers, etc this means trigger pulse width and delay is dependent on what needs to be triggered. The timing box can be used like an old player piano (pianola) where sets of triggers can be programmed and played back to ensure we trigger a laser and cameras in synchrony.

## Communication Protocol

The timing box communicates with a host PC using a standard 8n1 serial protocol using a FTDI USB-to-serial cable and a series of commands at a baud rate of 115200. Each command starts with an 8-bit opcode, followed by a command-specific number of parameter bytes. Commands are variable length; all lengths below include the opcode. Multibyte integers are sent most-significant byte first (big-endian). Some commands give responses and where appropriate below these are denoted as a call and a response to keep to the musical theme. Replies contain only the stated payload, without an echoed opcode or general acknowledgement. Serialize commands and wait for each defined reply before sending the next; commands without replies can be batched.

## Flashing Firmware

I've only ever used the Raspberry Pi Pico extension in VSCode for compiling, and flashing, my projects. It works fine and I'm sure there are other ways of doing this but I never found a need to seek out a different solution. Following the guide [here](https://www.raspberrypi.com/news/get-started-with-raspberry-pi-pico-series-and-vs-code/) walks through what you need to do. It's also possible to just drag and drop the uf2 file generated by the extension onto the Pico. Hold BOOTSEL during reset/power-on, release it when the USB boot device appears, then copy the UF2. Pressing BOOTSEL alone while firmware is already running does not reset the board. If the FTDI cable still supplies power, unplugging only the Pico USB cable may not reset it.

The current CMake target is Pico 2 (`PICO_BOARD=pico2`), with timing calculated for a nominal 150 MHz system clock. Check the target before building for another board. See [Development flashing over native USB](#development-flashing-over-native-usb) for the additional software-assisted flashing workflow; the VS Code workflow above remains an option.

## Quirks of PIO State Machines

I used the PIO state machines to control sending pulses through the BNC's and the clock we use for scheduling future triggers. In the individual .pio files I have written documentation, but I thought I'd include some pertinent / fun information and some justification for using them. These musings were originally written about a year after the original work; the hardware details below have since been corrected.

The RP2040 in Pico has two PIO blocks, and the RP2350 in Pico 2 has three, each with four state machines. These run independently from the main executable code, allowing lower-overhead, deterministic operations. Each state machine has X and Y scratch registers, an ISR (input shift register) and an OSR (output shift register). The CPU exchanges data with the state machine through its TX/RX FIFOs; it does not directly read and write those four internal registers. This firmware sends duration/mask pairs to one state machine and requests clock samples from another.

A key reason for using these is that we get consistent, trustworthy timing. Instructions normally take one PIO clock cycle, but programmed delays add cycles and blocking instructions can stall waiting for data. Once the data is available, execution does not depend on compiler or kernel overheads. State machines can also operate in sync with each other. The main downside is that we have to write instructions in a low-level assembly-esque language which requires a touch more brain power than writing ordinary C.

In the pio files I annotate each line in plain English. There is a useful Pico board [datasheet here](https://pip-assets.raspberrypi.com/categories/610-raspberry-pi-pico/documents/RP-008307-DS-1-pico-datasheet.pdf); for the PIO instruction set, use the microcontroller datasheet linked from the [Pico-series documentation](https://www.raspberrypi.com/documentation/microcontrollers/pico-series.html). Additionally, for setting up the PIO blocks and communicating with them, there is another useful [API reference](https://www.raspberrypi.com/documentation/pico-sdk/hardware.html#group_hardware_pio). This links to the PIO library, but similar documentation exists for the other libraries included.

## Output mapping

The mappings are currently fixed. SET_PinSource does not change them.

| Pianola bit / output index | GPIO | Output |
|---|---|---|
| 0 | 2 | BNC output 0 |
| 1 | 11 | BNC output 1 |
| 2 | 14 | BNC output 2 |
| 3 | 15 | BNC output 3 |
| 4 | 25 | Onboard LED |

Bits 5-7 are ignored. The green/blue status indicator on GPIOs 26/27 is separate
from the onboard LED driven by bit 4.

## Timing model and known timebase mismatch

Sequence durations use nominal 2.56 us ticks. At the configured 150 MHz, an output
tick takes exactly 384 CPU cycles: 32 PIO cycles with divider 12. The reported
clock instead uses ten PIO cycles and a divider intended to be 38.4. Its 16.8
fixed-point representation rounds that to 9830/256 = 38.3984375, giving an average
clock tick of 2.559895833 us. It therefore counts about 40.69 ppm faster than the
output timebase (about 40.7 us per second). Both use the same system clock; this
relative scale error is separate from absolute oscillator accuracy.

A possible fix is a 12-cycle clock loop with integer divider 32, making both
paths exactly 384 CPU cycles. This is **not implemented**: normal, response and
wrap paths would all need balancing and testing. See the
[test documentation](tests/README.md#interpreting-the-divider-warning) for the
associated warning. Changing the existing divider alone cannot represent 38.4
exactly.

Correct output spacing assumes the next duration/mask pair arrives in time.
If the CPU feeder is late, the current mask is held until the pair arrives;
subsequent durations are not shortened to catch up. Native tests do not establish
a measured minimum reliable duration on hardware.

## Command Set

- SET_Pianola => 0x01
- SET_PianolaFinalPos => 0x02
- SET_PianolaRepeatFrom => 0x03
- SET_PianolaRepeating => 0x04
- RUN_Pianola => 0x05
- SET_PianolaFireTime => 0x06
- IRQ_StopAndReset => 0x7
- GET_CurrentPianolaTime => 0x08
- SET_PinSource => 0x09
- GET_PinSource => 0xA
- SET_CameraClk => 0xB
- SET_PIVParams => 0xC
- ENABLE_PIV => 0x0D
- GET_FirmwareVersion => 0xFD
- IRQ_DumpLog => 0xFE
- IRQ_HARDRESET => 0xFF

Below the action of each command in the protocol is defined as well ad the format of call and the response.

### SET_Pianola => 0x01

Set the entry at the given address (0-255) to the specified output mask and duration in nominal 2.56 us ticks. Each bit specifies a level: 0 low, 1 high. Adjacent entries can keep a bit high continuously, and the final pattern stays latched at natural completion. Zero duration uses the minimum of one tick.

Call: CMD, pianola address, pin mask, duration (3 bytes) = 6 bytes. Response: none.

### SET_PianolaFinalPos => 0x02

Sets the inclusive address of the final instruction in the pianola. Entries uploaded beyond this address do not execute.

Call: CMD, final address = 2 bytes. Response: none.

### SET_PianolaRepeatFrom => 0x03

Sets the pianola repeat address: the first pass starts at zero, later passes start here. Repeating can be stopped using SET_PianolaRepeating. At each repeat boundary, the repeat address is checked against the final address. If it exceeds final, playback finishes the current pass without repeating, becomes READY after the active/queued work completes, and retains the final output pattern. The stored repeat settings are preserved; they are not clamped or rewritten. Validation is deferred until use so uploads can set the repeat address before the final address, and live edits that shorten the sequence cannot strand playback.

Call: CMD, repeat address = 2 bytes. Response: none.

### SET_PianolaRepeating => 0x04

Sets the flag to repeat the pianola: 0x01 repeats until heat death of the universe and 0x00 disables repeating. The low bit is used. Changes are checked at sequence boundaries, subject to already prefetched work; use IRQ_StopAndReset for immediate cancellation when the command is serviced.

Call: CMD, repeat flag = 2 bytes. Response: none.

### RUN_Pianola => 0x05

Starts or restarts the pianola at entry zero, discarding old active/queued work and cancelling any pending scheduled start. It repeats if repetition is configured; otherwise it runs once. The reply is a clock sample taken after starting, not a hardware capture of the exact first pin transition.

Call: CMD = 1 byte. Response: pianola clock time = 3 bytes.

### SET_PianolaFireTime => 0x06

Configure the pianola to start or restart at a future 24-bit clock time. It uses the configured repetition setting. The reply contains an acceptance flag (0 or 1) and a fresh clock sample. A new request replaces any previous pending start, even if the new request is rejected; rejection does not stop active playback. An accepted restart leaves current playback active until firing.

Time comparisons wrap modulo 2^24. The target must be strictly in the future and less than half a cycle ahead (nominally about 21.47 seconds). The manager fires on the first poll at or after the deadline; actual pin changes also have PIO startup latency. Allow for host/USB serial latency when choosing the lead time.

Call: CMD, future fire time (3 bytes) = 4 bytes. Response: accepted flag, sampled clock time (3 bytes) = 4 bytes.

### IRQ_StopAndReset => 0x7

Stops playback, cancels active/queued output work and any scheduled start, disables repetition, and rewinds to entry zero. It applies entry zero's mask and holds it indefinitely, ignoring its duration. Stored instructions remain intact. This deliberately differs from XMOS, which resets its position but retains the last applied pattern. See [Stop and restart semantics](#stop-and-restart-semantics).

Call: CMD = 1 byte. Response: none.

### GET_CurrentPianolaTime => 0x08

Gets a fresh 24-bit clock sample from the timing box, sent most-significant byte first. See the timebase caveat above.

Call: CMD = 1 byte. Response: current pianola time = 3 bytes.

### SET_PinSource => 0x09

In the XMOS protocol this selects a logical source bit for an output, with optional inversion; it does not set GPIO input/output directions. The Pico consumes the packet but currently ignores it. Its fixed mapping is reported by GET_PinSource.

Call: CMD, output index, source bit index, inversion flag = 4 bytes. Response: none.

### GET_PinSource => 0xA

Gets the reported configuration for the queried output. The Pico reports output indices 0-4 mapped to the same-numbered pianola bit, with inversion 0. Other indices report source 29 (OFF), inversion 0. This does not implement configurable constant-OFF routing on the existing outputs.

Call: CMD, output index = 2 bytes. Response: source bit index, inversion flag = 2 bytes.

### SET_CameraClk => 0xB

The XMOS command sets an additional clock's half-period in nominal pianola ticks (2.56 us). The Pico currently stores this value only; it does not generate camera clocks. Indices 0-7 are stored; higher indices are ignored after consuming the complete packet.

Call: CMD, clock index, half-period (3 bytes) = 5 bytes. Response: none.

### SET_PIVParams => 0xC

The XMOS command configures PIV. The Pico decodes and stores the parameters but does not generate PIV pulses or monitor camera exposures. The four timing values are unsigned 32-bit big-endian integers in **10 ns units**, not 2.56 us pianola ticks. They are inter-pulse interval, pulse length, gap before exposure end, and expected exposure length, in that order. The final field is an exposure-input bit index, not a bit mask. The channel placeholder does not provide multiple working PIV engines.

Call: CMD, channel index, four timing values (4 bytes each), exposure bit index = 19 bytes. Response: none.

### ENABLE_PIV => 0x0D

This command exists in the reference XMOS firmware. The Pico consumes both parameters to preserve packet framing, but enabling/disabling PIV is currently a no-op.

Call: CMD, channel index, enable flag = 3 bytes. Response: none.

### GET_FirmwareVersion => 0xFD

Returns the current protocol version and earliest compatible protocol version, currently 6 and 6. These numbers do not identify a particular build or imply that all XMOS features are implemented.

Call: CMD = 1 byte. Response: current version, earliest compatible version = 2 bytes.

### IRQ_DumpLog => 0xFE

Returns a fixed 1024-byte binary dump: 32 records of 32 bytes. Each queued record starts with the response payload length, followed by that many response bytes and zero padding. These records log replies, not all received commands. New records are discarded if the debug queue is full. A dump drains the included records in FIFO order and fills unused records with zeros.

The complete dump is transmitted before any later response. This Pico-specific format differs from the reference XMOS diagnostic output. Sending 1024 bytes occupies about 89 ms at 115200 8N1, but core 0 transmits incrementally rather than blocking playback for that whole time.

Call: CMD = 1 byte. Response: 1024 bytes.

### IRQ_HARDRESET => 0xFF

Cancels active and queued playback, drives all sequence outputs low, and clears
the stored sequence, scheduled start, repeat settings, and camera-clock and PIV
settings. Send one opcode byte. The command sends no reply. This is an in-place
reset: the independent clock and UART keep running, and the CPU does not reboot.
It does not flush the UART command/response queues or debug log.

Ordinary live sequence edits are not atomic: already queued entries may use the
old data. Program while stopped when consistent replacement matters. UART
buffering is finite, with no RTS/CTS or checksum. Partial packets are retained
without blocking TX service, but are not timed out. A reset-byte train can help
recover framing while command servicing is alive; it cannot guarantee recovery
from a fault or deadlock. There is no hardware watchdog.

## Native regression tests

Run `python3 tests/run_tests.py` on macOS without a Pico or Pico SDK. The suite
runs the actual firmware C with fake peripherals and checks the actual PIO source
with a limited instruction model. Functional failures and timing warnings are
reported separately. Existing bugs deliberately produce failures.

See [tests/README.md](tests/README.md) for prerequisites, filters, exit codes,
coverage, limitations and occasional hardware-validation guidance.

For a connected Pico, `python3 tests/hardware_stress.py --list-ports` lists
candidate serial ports. Omit `--port` to choose from the available USB-serial
ports, or specify it explicitly for unattended stress checks; add `--interactive` for optional human onboard-LED observations. This
replaces/runs the device's pianola. See the connected-device section in
[tests/README.md](tests/README.md) for instructions and validation limits.

## Development flashing over native USB

The FTDI UART and Pico native USB are separate interfaces and can be connected
at the same time. The modification/flashing notes already describe that setup.
BOOTSEL is entered on a reset with the button held; it is not a permanent mode
or a one-time provisioning step. Normal firmware starts again after flashing.
If the FTDI connection still powers the board, unplugging only native USB does
not necessarily reset it.

Production builds keep native USB disabled by default. For software-assisted
flashing, configure a development build (from this repository):

```sh
cmake -S . -B build/usb-flashing -DTIMINGBOX_USB_FLASHING=ON
cmake --build build/usb-flashing
```

Once, enter BOOTSEL manually and load
`build/usb-flashing/picoTimingBoxFirmware.uf2`. Thereafter leave both cables
connected. Compatible running firmware exposes the SDK's USB reset interface;
`picotool` can reboot it into BOOTSEL, verify/load a new image, and restart:

```sh
picotool load -f -v -x build/usb-flashing/picoTimingBoxFirmware.uf2
```

Use a device serial-number selector if multiple Picos are connected. Keep
`TIMINGBOX_USB_FLASHING=ON` in subsequent builds to retain this convenience.
The native USB CDC port is distinct from the `/dev/cu.usbserial*` FTDI port used
by the application/stress tests. This option does not move the timing-box
protocol to native USB or alter the UART baud rate.

The option explicitly disables waiting for a USB host at startup and blocking
USB stdout timeouts. USB still adds SDK background interrupt work (normally on
core 0), so it is optional and its timing under load requires device validation.
It is not a guaranteed recovery path for a completely wedged firmware; BOOTSEL
with a physical reset/power cycle or an SWD debug probe remains the fallback.
No watchdog has been added by this change.

## Stop and restart semantics

`StopAndResetPianola` now cancels the output state machine's active and queued
work, rewinds to entry zero, applies that entry's output pattern, and freezes on
it. Its duration is ignored while stopped; a nonzero pattern remains asserted.
Pending starts and repetition are cancelled. Stored entries are preserved. The
held pattern is a snapshot at stop, not an automatic subscription to later edits.
This deliberately differs from the reference XMOS stop handler, which rewinds
its position but retains the previously applied pattern.

Immediate run/restart discards old in-flight work, preloads entry zero and begins
again without inserting an all-low pattern. Configured repetition survives a
restart. Scheduled firing uses the same cancellation/start path at firing time.
Hard reset clears the output pipeline and holds the outputs low until the next
start. It runs in place, so the independent clock and UART continue serving
commands.

A transition emitted before the output SM is disabled cannot be undone. These
semantics take effect when core 1 services the command; they do not promise zero
UART/command latency.

During playback, the output state machine applies each entry's mask in one
write and holds the final mask at natural completion. Adjacent updates are
2.56 µs apart per requested tick when the next entry is queued in time. A zero
duration uses the minimum of one tick. If a successor arrives late, the current
mask stays asserted until the next complete pair is available.
